== About these notes

This file records the thinking behind the deck in `talk.sd`, as dictated by the author while the slides are being planned. It exists because the slides only carry conclusions. The reasoning that picked those conclusions, and the order they arrive in, would otherwise live in one head. Each section below is a concept the talk has to land, written down before or alongside its slides, so the slides can be checked against the intent.

The existing deck is kept. Everything here is additive to it. Full references for anything a slide asserts are in `docs/refs.bib`.

== The framing problem

The talk is meant to give an overview of ChRIS. The author is its chief architect and finds that hard to do, which is not an accident: the person who knows every layer has no natural stopping point, and an explanation only works if it matches the audience. The HARBOR audience is technical. The aim is still to keep things simple.

The chosen approach is to start from first principles, on a conceptual footing, and build up from there. The deck does not open with components or features. It opens with the question of what it means to define a piece of technology at all.

== Concept 1: the lightness of defining a product

=== What it is

A new first entry on the outline, "The Unbearable Lightness of Defining", after Kundera's novel <<kundera1984>>. The title was first floated as "The Unbearable Lightness of Being"; "Defining" keeps the echo and says what the section does. The entry opens a second menu that runs a thought experiment: what is an iPad?

=== The thought experiment

Everyone knows what an iPad is. Ask them to define it and few can. The experiment walks through the answers people give and shows each one giving way.

One answer is that it is a mobile OS. The counter is to ask what a mobile OS is, and whether that is a different kind of thing from a non-mobile OS. The answer has only traded one undefined word for another.

Another answer describes the experience: a device that shows pictures of applications, and touching a picture starts the app. The apps do things like report the weather, show the news, or play a game. So an iPad (or an iPhone, or any tablet or phone) is little pictures that do things.

The counter to that is to change the whole UI. On Android this is entirely possible. The author's own phone runs Re:T-UI <<retui>>, a launcher whose home screen is a command line: no icons, no pictures, a prompt. By the pictures definition it is no longer a phone, which is absurd.

=== The author's own definition

An iPad is a computer running a bespoke fork of macOS, with a deliberately restrictive app model that often runs against the grain of the OS underneath it: sandboxed apps, no `fork`, no pipes between apps, no universal access to the file system. Put bluntly, for the sake of security it is a crippled macOS behind a very restrictive UI.

=== The point, sharpened

As first dictated, the point was that people define a thing by how they experience it, and that this experience is entirely subjective. Left there, it undercuts the author's own definition, which is offered as the better one while being just as much a product of how an architect meets the device.

The sharper version, agreed in discussion, keeps the subjectivity and adds a test. A definition by experience describes the interface. A definition by construction says what the thing can and cannot do. Swap the launcher and "pictures you touch" becomes false, while "sandboxed apps, no pipes, no shared files" stays true. The definition worth keeping is the one that survives a change of UI. The slides say outright that the architect's answer is subjective too, so the claim is not that one view is objective. It is that one of them is stable.

=== The bridge to ChRIS

ChRIS has the iPad's problem. Ask five people what it is and each describes how they met it: a dashboard for running analyses, a full web UI with a shell that looks like a whole computer, the thing that pulls studies out of a PACS from the CLI, a persistent record of all analyses and transformations, a workflow engine. Each is true and each is a "pictures you touch" answer. The first three are the telling ones. They come from people who met ChRIS_ui, ARGUS and `chell`, and they describe three different products while the ChRIS underneath is the same one. The HARBOR audience has already seen ARGUS, so for them the swap is something witnessed and not hypothetical. The fourth answer comes from someone who met a feed and the fifth from someone who met a pipeline. The same test applies. Swap any of the three surfaces for another and it is still ChRIS, exactly as the author's phone is still a phone. `chell` and ARGUS are the shell and web surfaces of `mise` <<mise>>. (`mise` presents ChRIS as a POSIX-like computer. An earlier draft of the slide named `chrs` here, which is deprecated.)

Between the two halves sits a mapping the author proposed after the section was first built. The iPad was brought in to show how hard a common computing object is to define, and it can also be read as a model of ChRIS. Darwin, the core that iPadOS and macOS share, stands for CUBE. iPadOS is Darwin under SpringBoard, the process that draws the home screen and launches apps, and that stands for CUBE under ChRIS_ui. macOS is the same core with the whole computer exposed, and that stands for CUBE under `mise`, with Terminal against `chell` and the desktop against ARGUS. The Mac's login window stands for `porter`. So the "pictures you touch" answer was a description of SpringBoard, and "a dashboard for running analyses" is a description of ChRIS_ui.

An objection is that an iPad and a Mac are separate machines while ChRIS_ui and `mise` face one CUBE. The author's reply is that the machines are no longer separate in any way that matters: a current iPad Pro carries the same M-series chip as a Mac <<appleipadprom4>>, the kernel is the same one <<applexnu>>, and Apple states that unmodified iPad apps run on a Mac with Apple silicon with no porting <<appleiosappsmacos>>. What separates the two is what a process is allowed to do. That is the slide's claim about ChRIS as well: one CUBE, and the surface decides how much of it a person can reach.

The author also weighed Android over Linux as the comparison. That pair shares a kernel and little else, and its apps don't cross. ChRIS resembles Apple below the line, with one kernel and one app model, and Android above it, since ChRIS_ui and `mise` share nothing but CUBE's API. The slide stays with Apple because the section is built on the iPad and because apps crossing is the property that carries over. Android is left for a spoken aside.

The mapping casts ChRIS_ui as the restricted side, and the author accepts that. By the author's account ChRIS_ui is a dashboard directly over CUBE that has not been worked on in more than a year, and `mise` is its successor. The slide says only that one is the dashboard and the other the computer. Succession is a fact about ChRIS and no part of the analogy, since the iPad is not being retired for the Mac. The login row is the weakest: an iPad has a lock screen and ChRIS_ui has its own login, so login does not tell the two sides apart. Elsewhere the deck compares `porter` to `gdm`, and that comparison stands.

The second half of the bridge is the one that sets up the rest of the deck. The author's iPad definition is a list of what apps are forbidden to do. ChRIS is also defined by a restrictive app model: read a directory, write a directory, exit. The two restrict in opposite directions. The iPad keeps apps apart, for isolation. ChRIS restricts apps so that they compose. The iPad forbids the pipe between apps, and ChRIS is the pipe. This hands straight over to the existing "App Contract" section, which now arrives as the answer to a question the audience has already been made to ask.

=== How the claims are sourced

"Fork of macOS" is the author's spoken phrasing and is loose. The slide says "a close relative of macOS" and the figure says "same kernel (XNU), same core (Darwin)", which is what Apple's own kernel source states <<applexnu>>.

That every third-party app is sandboxed, and that each has its own home directory for its files, is from Apple's platform security guide <<appleplatformsecurity>>.

That iOS apps may not spawn child processes is from a reply by an Apple support engineer on the developer forums <<appleforum747499>>. It is a forum post and not formal documentation, and the same reply notes that the iOS sandbox is a different mechanism from the macOS App Sandbox.

"No pipes between apps" has no direct source. It follows from the two restrictions above: without a common parent process or a shared place in the file system, two apps have no way to hold the two ends of a pipe. It is flagged here as an inference.

=== How it was built

The section is a menu inside a spoke. The outline entry lands on the "What is an iPad?" menu, whose four entries are the answers a room might give, the architect's answer, and the bridge. Each opens a short run of slides and returns to the menu, so the presenter can open whichever answer the audience offers first. Advancing from the menu itself returns to the outline. The menu slide opens on its title and question alone. The `whatis ipad` command and the four entries sit in one reveal and wait for the first Right key, so the author can put the question to the room before any answer shows.

Of the five answers on the "So What Is ChRIS?" slide, four are the author's wording: the dashboard, ARGUS, `chell` and feed answers. == Architecture revision: pfcon alone, and mise above CUBE

=== What it is

A correction to the existing "Architecture" slide and two new slides after "Who Owns What". The two slides were later moved into the mise section, described further down, under the addresses `mise-machine` and `mise-layers`. The correction removes `pman`. The figure used to show a `pfcon+pman` pair per compute environment and now shows `pfcon` alone, with `mise` added beside ChRIS_ui as a second client of CUBE's REST API. The new slides are "ChRIS as a Computer" (`architecture-posix`) and "Above CUBE" (`architecture-posix-2`).

=== Why

The author's instruction was that `pman` is deprecated and that the architecture should pull in ideas from `mise`, described as a core part of the POSIX-leaning extensions to ChRIS. The old figure taught the audience a component they will never deploy. The old architecture section also stopped at CUBE on the client side, with ChRIS_ui as the only thing above it, which contradicts the opening section's claim that the UI is one way among several to meet ChRIS.

=== How it relates to the existing slides

"Who Owns What" already layers the system downward from CUBE: meaning, mapping, execution. "Above CUBE" layers it upward in the same figure style, using the four-line statement at the head of the `mise` README <<mise>>: CUBE says what is true, `mise` says where things are, Calypso is who is there, `chell` and `argus` are how you look. The pairing gives the section one sentence to close on: below CUBE the cluster can be swapped, above it the surface can be swapped. That sentence is the assistant's. It is the architectural form of the test from Concept 1, and it returns to ChRIS_ui, ARGUS and `chell` as the three surfaces named there.

"ChRIS as a Computer" shows four shell lines taken from the `mise` README: `cd` into a data directory, `ls /bin`, run a plugin by name, `cat` a job's status under `/proc`. The right-hand glosses are shortened from the README's own comments, except "a running job is a file", which paraphrases its "every running job a file you can read". The takeaway, "a machine instead of an endpoint", is the README's phrase.

=== How the claims are sourced

That `pman` no longer exists as a separate service is from the `pfcon` repository's history: commit `bf65ddf`, "Merge pman (#149)", dated 2025-09-25, followed by "Remove some remaining pman references" <<pfcon>>. The slide's list of compute environments is narrowed from the `pfcon` README, which names Docker, Podman, Swarm, Kubernetes and SLURM. OpenShift is carried over from the earlier slide and is not named in that README.

Everything on the two new slides is from the `mise` README in the author's local checkout at `96ce597a`. Neither repository was read from GitHub.

=== Open points

`pfdcm` is still on the "Architecture" slide as half of the PACS bridge. The author named only `pman` as deprecated, so `pfdcm` was left alone. It should be confirmed.

The slide's source line still cites `FNNDSC/CHRIS_docs`. The `miniChRIS-docker` citation was dropped from that line because its README still lists `pman` as a component.

"Who Owns What" was not changed. Its three layers never named `pman`.

== The mise section

=== What it is

A new outline entry, "mise: ChRIS as a Computer", placed after "Architecture". It opens a menu of five short runs: a machine and not an endpoint, the layers above CUBE, the intent kernel, one session with many surfaces, and the door and the berth. The first two are the slides that were added to the architecture section earlier the same day, moved here. The first was retitled from "ChRIS as a Computer" to "A Machine, Not an Endpoint", because the section itself took the former as its heading and a menu entry has to read the same as the slide it opens. The other three are new. The author asked for it on 2026-11-11 with the words "we need a part on mise too" and "where needed add more nexus spin offs".

=== Why

`mise` is the author's answer to the question the opening section raises. If ChRIS is defined by its app model and the UI is one way to meet it, then something has to make the other ways cheap to build, and that is what `mise` does. It also carries the author's position on scheduling, which is why it replaced the Airflow material.

=== How it relates to the existing slides, and to HARBOR

The current HARBOR authority does not mention `mise`, `chell`, ARGUS, `porter` or berths. The section therefore sits with the architecture, as ChRIS engineering, and none of its slides cite HARBOR. The architecture section now ends on "Who Owns What" and keeps `mise` only as a box beside ChRIS_ui in its component figure.

=== How the claims are sourced

All five slides are drawn from the `mise` repository <<mise>>, read from the author's checkout at `96ce597a`: the README for the first two, `docs/intent-kernel.adoc` for the kernel, `docs/calypso.adoc` for the session, and the README with `docs/berths.adoc` for the door and the berth. The repository has moved from the FNNDSC organisation to `HARBOR-Medical-AI/mise`, and citations were corrected to match.

The session working in the `mise` repository checked thirteen claims from these slides on 2026-11-11 against `main` at `550b1d23`, reading code and docs without walking the lines on a live CUBE. Its corrections were applied the same day.

The `/proc` path in the shell figure was wrong in shape. A job's node nests under its parent, and a plugin run from a plain folder hangs off `pl-dircopy`, so the path now reads `/proc/jobs/feed_123/pl-dircopy_456/pl-fshack_789/status`.

The kernel slide's last bullet said loops and branches stay in the caller's script. The rule stands for loops and `if`, but `chell` gained `&&` and `||` lists that day, beside `;`, variables and `$(...)` capture. The bullet now says "no loops, no if". The receipt is real, with a caveat for the speaker: only a minority of commands return a typed model so far, and most receipts are still text.

The kernel slide's takeaway said nothing above the kernel touches the raw API. That was wrong. `porter`, `stratus` and two places in `salsa` speak HTTP to CUBE directly. The documented rule is about surfaces, so the takeaway now reads "no surface touches the raw API".

On the session slide, the claim that the engine sits where the data stays is a design property whose means are in place; a spoke deployment with egress policy is still design. The bullet now says the engine can sit there.

Berths are partly shipped. A container per person behind `porter`, with `/incoming` and `/outgoing` mounted and a shell that is never the CUBE host's, exists where a deployment turns it on. The commands that anchor a node's output to `/incoming` and send results back to a feed are not built, so nothing flows through a berth yet. The slide says "shipping in stages".

Three questions were settled along the way. There is no scheduler and no trigger of any kind in `mise`; the phrase "berth trigger" matches nothing in its code or docs. `pfdcm` is live and is CUBE's server-side query and retrieve service, so it stays on the "Architecture" slide. The two PACS paths are both current: `/net/pacs/queries` is the virtual tree of query results, and `/SERVICES/PACS` is where retrieved DICOM is stored.

"A Machine, Not an Endpoint" was rebuilt on the author's instruction as a `chell` session instead of a static figure. The presenter types `chell`, and each click then shows a `chell` prompt, types one command after it, and prints that command's output in one step when the typing ends. The blinking cursor sits after the command being typed.

The output lines were captured live by the `mise` session on 2026-11-11 from `chell` 5.20.7 on a test CUBE, read-only, with the user, host and folder name replaced by neutral ones. Four departures from that capture are deliberate. The real prompt prints the full CUBE API address where the slide says `cube`, shortened for width. The third step is `whatif`, which resolves a run and starts nothing, because capturing a real run would have started a job; its output is cut from four lines to two and the first of those loses its trailing title. The status word `finishedSuccessfully` is what CUBE reports but was read from a node of a different plugin. The plugin version is the one on that CUBE, v1.5.0, where the README example says v1.2.0.

The first build of this slide needed raw HTML and three CSS rules in the deck, which the author rejected: the `.sd` source should not be awkward. The behaviour was moved into slidedown instead, on a branch named `term-nested-typewriter` in the author's checkout. A typewriter inside a reveal now carries the terminal cursor, a prompt appears at once, only the command is typed, and the lines beneath a command are printed together. The slide's source is now four plain `.o{.typewriter{...}}` blocks. The dim glosses that sat beside each result ("data is a filesystem" and the rest) were dropped with the raw HTML, and the takeaway line carries them. Until that slidedown branch is merged and the pin in `.github/workflows/pages.yml` is moved to it, the published deck will type the output letter by letter and put the cursor under it.

"The Whole Stack" puts the architecture figure from the `mise` README on a slide of its own, on the author's instruction. The author had found the deck's small figures weak and pointed to that figure as the standard: three machines and two networks, nested boxes, layers stepped like a staircase, and a note in the right margin for every row. It is reproduced as the README has it on `main`, with the component names coloured and the margin notes dimmed. It is 51 rows by 125 columns, so it is set at about three quarters of the deck's figure size and runs to nearly twice the height of the page. The author accepted that on the condition that the Up and Down keys move the window over it. slidedown did not do that, so it was added on a branch named `slide-pan` in the author's checkout: on a slide taller than the page the two keys pan and never leave the slide, and on every other slide they still go to the first and last slide. The other figures in the deck have not been redrawn. This one is the test of whether the style reads from the back of a room.

The author then asked for one intent shown from each way in: the shell, a JavaScript program, and an API, using the listing of files as the example. That became a sixth entry in the mise menu, "One Intent, Four Ways", which is itself a menu of four slides. The `mise` session supplied all of the material on 2026-11-11.

"From the Shell" is an `ls -l` captured live from `chell` 5.20.7, with identifiers replaced. "From a Program" is the typed `chell` API from `@fnndsc/brasa`, which is shipped, runs in-process, and runs on Node only. It began as an excerpt from the mise guide. The author then asked that it follow the TypeScript style guide, so it was rewritten by the agent as one documented function, `directoryNames_list`, with explicit types on every binding. The type names (`ChellApi`, `TypedEnvelope<'fs.listing'>`, `ListingItem`) were read from the `mise` source on `main`. The `mise` session typechecked it against `main` on 2026-11-11. The agent's first version passed plain strict mode and failed the style guide's own baseline, which turns on `noUncheckedIndexedAccess`, because it indexed `data[0]` without a guard. The version on the slide is the session's correction, which compiles clean under that baseline. It was typechecked and not run, and it assumes a connection already made with `chrisConnection_init`, which the slide's source line says. "Over the Wire" is the calypso session protocol over a WebSocket. Its request and response were derived from the schemas in `@fnndsc/menu` and were not captured from a running session, and the slide's source line says so. The author had asked for an API entry. The `mise` session advised against presenting one as HTTP, because a stateless HTTP facade for intents is planned and not built, so the slide says that in a bullet. "Without mise" is the fourth way and was the `mise` session's suggestion taken up by the agent: the six REST calls the same listing costs against CUBE directly. The three folder collections are named on the slide by link relation, since their literal paths were not verified.

The program and the wire exchange are syntax coloured with slidedown's `.code{.syntax{...}}` block, in TypeScript and JSON, on the author's instruction that any code or API material shown must be coloured. The colours are the theme's configured Pygments style, Monokai, which is louder than the rest of the terminal palette; a calmer style would be a one-line change in the theme and is the author's to choose. The REST list on "Without mise" stays a figure with its verbs marked.

Two things on these slides are known to be softer than they look. Models cross the wire untyped today. And the mise guide's own page understates which commands are typed, so the slide follows the code and not that page.

The docs site is `harbor-medical-ai.github.io/mise`. The page addresses on the source lines were derived from how the site is built and were not opened in a browser.

The layers figure is the docs' own four-line metaphor and is simpler than the code, where "mise" names the whole stack and the layers are `chell` and ARGUS, `porter`, `calypso`, `brasa`, the virtual filesystem, the CUBE driver, and CUBE.

== HARBOR slides: re-checked against the current authority

=== What it is

A rewrite of the five HARBOR slides and of two stray HARBOR lines elsewhere in the deck, done on 2026-11-11.

=== Why

The author asked why Apache Airflow kept appearing. It traced to the LaTeX TDD the slides had been written from, which has been retired. The session that maintains the current HARBOR milestones work was asked to mark twenty claims from the slides as supported, changed, or absent. Its answers are the basis for every change below. The deck's agent did not read the authority itself, so this section reports a second-hand check, and the author is the one who can confirm it.

=== What changed

"Where ChRIS Sits in HARBOR". The Hub's role is wider than the old figure said: it is a marketplace and it orchestrates and audits, and it runs ChRIS too. ChRIS is in every Trusted Domain and not only in the Spokes. What flows back up is derived results, under permissions. The old third bullet, that policy belongs to HARBOR and ChRIS only supplies the record, was dropped because it no longer holds. The airport metaphor ("apps are aircraft: machinery flies in, no raw data flies out") came off the slide for length and is worth saying aloud.

"The Boundary". The runtime now also enforces what an app may do beyond reading and writing its directories, so a line was added for that. The list of what ChRIS leaves alone is an inference from how the work is divided and is not stated anywhere as a list. The old line about what ChRIS hands the platform teams was not checked and was removed.

"Ingestion as Apps", formerly "Ingestion as Plugins". The authority says "app". "Quarantine" is not its word: invalid images are rejected with a report, so the figure's failure branch now says that. A named embedding model and the phrase "three health systems" were removed, the first because it is now only an early benchmark and the second because it is not in the authority. The order of work is also reversed from what the slide said: the stages are composed into one workflow first and each app matures afterwards.

"What HARBOR Adds to ChRIS". The old slide said today's runtime is synchronous and that the funded work is asynchronous execution for workflows of thousands of nodes. None of that is in the current authority. What is there: dispatch from the Hub to a named Spoke, telemetry with one record per run, handling of a Spoke that fails or stalls, and a baseline measured first and re-measured at volume. The figure's top layer is now the Hub. The takeaway changed from throughput to running the contract across a federation. A bullet the agent had added earlier that day about `chell` under cron was removed, because the authority says nothing about `mise`.

"Governance and Standards". Data use agreements and quotas at the orchestration layer were removed: agreement rules live with security and compliance, and quotas are not in the authority. The lineage line now says "OpenLineage-compatible export", which is the authority's weaker wording. The three DICOMweb services are still right but belong to a different section of the document than the slide used to cite.

"Workflows and Provenance". The line saying HARBOR's documents call the directory contract the "filesystem-bus" was replaced. That term is from the retired text. The current wording is that applications and workflows communicate through storage.

"What We Need to Agree" (since cut, on 2026-11-12). "Policy hook points" became "App policy" and "Telemetry schema" became "Run record", to follow the changes above.

=== Style

These slides are the first written to the author's rule for word density, set the same day: short fragments, at most four to a slide, each with one highlighted word. "The Same Move, Reversed" was converted as a sample, and the rest of the deck followed later the same day. The sentences those slides used to carry are kept at the end of this file as speaking lines.

== A live chell on a slide

The author wanted a working `chell` inside the presentation, reaching a session on another of the author's machines, and observed that this is what the ARGUS console already is: xterm.js in a page, a websocket, and a real `chell` under a pseudo-terminal at the far end. That reading is right. In ARGUS the far end is `calypso`, which starts `chell --remote` under `node-pty` and relays its bytes; the page only draws them and sends keystrokes back.

A slide cannot take ARGUS's place against a `porter` directly. `porter` relays the session's websocket only for a browser that carries its login cookie, and the cookie is `SameSite=Lax`, so a page served from another machine does not send it. Its door tokens are for scripts, which can set an `Authorization` header; a browser cannot set one on a websocket. Loosening either for a talk would weaken the door for everyone.

The slide therefore keeps the three parts and moves the middle one to the presenting machine. `ttyd` <<ttyd>> serves xterm.js on loopback and bridges it to one command under a pseudo-terminal, and that command is the author's own `chell --remote`, attached to that session. The login stays with `chell` on the presenting machine and nothing about it is in the deck. `ttyd` is bound to `127.0.0.1` and checks the origin of the websocket, so only its own page on that machine can open the terminal. Binding it to a LAN address would hand a shell to the network.

The slide (`mise-live`, "A Live chell") shows a line to click. The click loads the terminal in a frame only when the deck was opened as `localhost`; on the public site or another device it prints that the live session runs on the presenting machine only. Nothing connects until the click, so no session is held open through the talk, and a visitor to the public deck triggers no request to their own machine. A click in the frame gives the terminal the keyboard and a click outside returns the arrow keys to the deck.

A custom bridge, with xterm.js bundled into the deck, was the alternative. It would have been more code to trust on the day and would still have needed a pseudo-terminal library installed, and `ttyd` is one package.

== How one ChRIS talks to another

=== What it is

Three slides added to the "What HARBOR Adds to ChRIS" section on 2026-11-11, between its opening slide and "Governance and Standards": "One ChRIS to Another", "The Gaps Between Them" and "From Client to Peer". The last line of the deck's "Conclusions" slide was changed to name the same point.

=== Why

The author raised it as the obvious gap. Asked whether the WebSocket was the only way for one ChRIS to reach another, apart from calling the other CUBE's API directly, the agent's answer was that neither is one ChRIS talking to another: both are a client talking to a ChRIS. The author asked for a slide on that, with the gaps and a conclusion.

=== How it relates to the existing slides

== The architecture, built up in steps

The author's complaint was that the finished figure arrived all at once and ran off the page. The request was to add components a few at a time by moving quickly through slides that each show the same picture with more in it. The effect is built inside one slide instead of across six. Each step is a revealed line (`.o{}`) holding the whole figure as it stands at that step, and three rules in the deck's `css:` block collapse every step except the newest. === Where It Came From (`what-is-2`)

* pre-2010: bash scripts gluing analysis programs together.
* 2010 v1: a web front end over those scripts and an in-house HPC.
* 2013 v2: the ideas that stuck: feeds and plugins. Still HPC-bound.
* 2017 v3: REST services and containers. Any cluster that runs Linux containers. (Called CHIPS in the papers of that year.)

=== What ChRIS Promises (`what-is-3`)

* A developer writes the app the way they already do: files in, files out. Nothing in it is written for ChRIS.
* A system developer keeps their shell. The surface leans POSIX, and the whole platform can be driven from an ordinary bash script.
* The glue is the platform's job. Most of a developer's time goes to scripts that join tools together, and the data handling in those scripts is the part most often done badly.
* Because the contract is only files in and files out, the same app runs unchanged on Docker, on Slurm or on OpenShift.

This slide states as a thesis what the deck otherwise shows in pieces: the app contract, the shell in the mise section, and the history slide's "bash scripts as glue". The author asked for it on 2026-11-12, judging it an important idea that no slide said outright. It sits after the history slide because that slide ends on glue. The claim about where developers' time goes is the author's account from experience and carries no citation. The contract does not cover interactive programs, which the `what-is` slide already says, so "any app" is not claimed here.

=== The App Contract: start with a function (`contract`)

* Draw it first as mathematics: a goes into F, and b comes out. Written down, b = F(a).
* F is a mapper, a transformer. It turns a into b.
* a and b are materialized things. They exist, and can be looked at, before and after F runs.
* F must produce an output. Ideally it produces the same one each time: for the same a, we always get b.

The author asked on 2026-11-12 for the contract section to open this way, "almost a mathematical treatise", because the contract is the idea the rest of the talk stands on. The next slide redraws the same picture with `/input`, an app and `/output`, and labels them a, F and b so the audience sees it is one figure drawn twice. Both slides carry the title "The App Contract" so that the outline entry still names the slide it lands on. "Ideally" is on the slide on purpose: the platform records what ran, and does not by itself make a program deterministic.

=== The App Contract: on a command line (`contract-2`)

* A ChRIS app: a plugin: is a Linux container that reads one directory, writes another, and exits.
* It does not know about ChRIS, the workflow it sits in, or the cluster under it.
* A JSON descriptor declares its parameters and its limits: CPU, memory, GPU.
* Python, R, shell, compiled code, a call out to a model service. The boundary doesn't change.

=== Three Kinds of Plugin (`contract-3`)

* fs: feed synthesis. No input directory. Brings data in: a PACS pull, an upload, a download.
* ds: data synthesis. Input in, output out. Nearly everything is one of these.
* ts: topology synthesis. Reshapes the graph itself, joining branches into one node.
* De-identification, format conversion, segmentation, embedding, a training step: all ds.

=== One Contract, Not n APIs (`contract-4`)

* If tools call one another directly, every pair needs its own connection. That grows as n squared.
* A platform that reaches each tool through that tool's own API needs an adapter per tool. Its work grows with the number of tools: O(n).
* A platform that knows one contract learns nothing new when the next app arrives. Its work is constant in the number of apps: O(1).
* The same holds on the other side. With n apps and m kinds of compute, adapters would number n times m. With the contract between them it is n plus m.
* Each app still needs a wrapper, so the total work is not constant. The wrapper is small, it is written once by whoever owns the tool, and the platform never changes for it.

The author asked for this slide on 2026-11-12, recalling an earlier document that makes the argument. It is an unpublished position paper of the author's from January 2026, shared only with collaborators, so the slide restates the argument in the author's terms and carries no source line. The paper compares three patterns as the number of tools N grows: a mesh in which tools call one another directly (connections grow as N squared), an orchestrator that calls each tool's own API (N drivers to maintain, and the orchestrator carries the data between steps itself), and the filesystem contract, where the orchestrator's interface stays the same however many tools are added. The slide shows all three side by side; the mesh was first left as a spoken aside and the author asked for it as a third panel the same day. To keep four bullets, the line about n apps on m kinds of compute moved from the slide to the speaking lines above. Two of the paper's phrasings are deliberately not used: it calls the quadratic growth "exponential", and it puts the cost of adding a tool at "zero". The defensible claim, and the one on the slide, is a constant cost on the platform's side, with each tool still to be wrapped once. The n plus m line about substrates is the session's extension and is not in the paper. Points the paper adds that can be spoken here: large imaging data is read from a mounted volume instead of being serialised over HTTP, a crashed container leaves its data on disk, and a scientist's file-processing script is already the production code.

=== Wrap Before Inventing (`contract-end`)

* ChRIS doesn't need to own every anonymiser, validator, harmoniser or model runner.
* A good external tool gets a container and a declared interface. That's usually the whole job.
* What it gains: explicit I/O, recorded parameters, a pinned version, a place in a workflow.
* Write a plugin from scratch only when nothing adequate exists, or the plugin is the research.

=== Workflows and Provenance: start by linking them (`workflows`)

* One app: input, app, output. That is b = F(a) again.
* Its output is a directory, so it can be the next app's input. Add a second app and c = G(b).
* Add a third. Nothing new was needed to make a workflow: only the contract, used again.
* Chaining is composition: d = H(G(F(a))). The difference from mathematics is that b and c are kept on disk.
* Keeping them is what provenance is. The next slide shows the tree those kept outputs form.

The author asked on 2026-11-12 for this section to open with a drawing that builds, to show that linking follows from the contract without further machinery. The figure builds in three steps and the last one stays while the bullets arrive. The function names F, G and H, the composition line and the typewriter command are the session's additions to the author's sketch.

=== Workflows and Provenance: the tree (`workflows-2`)

* A workflow is a tree of plugin runs. One node's output directory is the next node's input.
* In HARBOR's terms: apps talk through storage.
* Every intermediate output stays where it was written, and stays inspectable.
* A feed is one such tree, run on one dataset. A pipeline is the reusable template for it.

=== Data State, Not Control Flow (`workflows-3`)

* Control flow is Argo and Tekton: a controller decides what runs next. Data state is Make, and ChRIS.
* A ChRIS node is finished when its output is on disk. Not when a controller says so.
* A loop does not hide in a controller. It is a branch: one node per item, each with its own directory.
* A join is a `ts` node: several parents in, one node out.
* So control is materialized in the tree, and the record holds it along with the data.
* The cost: patterns that are one line in Argo take an explicit step here.

The author asked on 2026-11-12 for the figure to show a branch node (a loop) and a `ts` join node, as "materializations of control in the tree", and judged that clearer than the earlier figure, which set a controller over three tasks against a straight chain of directories. The new figure fans one node out to three `segment` runs and gathers them in a join; the two control nodes are drawn in yellow. The earlier contrast now rests on the first bullet and the spoken lines, and the "done when on disk" and "the cost" bullets moved from the slide to the lines above. That control behaviour is relocated into the graph as explicit plugins is argued in an unpublished note of the author's on data-state and control-flow graphs. The series example and the directory names are the session's.

=== The Five Questions (`workflows-end`)

* What data went in?
* Which app ran, and which version of it?
* With what parameters?
* What came out?
* How did this final result come to exist?
* Answered by walking a directory tree. No log archaeology, no unordered database queries.

"How did this final result come to exist?" came off the slide; the takeaway and the last bullet carry it.

=== Architecture (`architecture`)

* CUBE: users, files, plugins, feeds, permissions, provenance. One REST API.
* pfcon: runs a plugin as a job on Docker, Kubernetes, OpenShift, or SLURM.
* pfdcm, oxidicom: the PACS bridge: query, retrieve, receive, register into CUBE.
* The slide no longer shows these as bullets. A caption beside the figure changes with each of its eight steps.

=== Who Owns What (`architecture-end`)

* CUBE owns meaning. pfcon materialises it. The cluster executes.
* One CUBE can drive several compute environments: a workstation, an HPC, a cloud.
* The lock-in test: can the same workflow still run somewhere without Kubernetes?

=== ChRIS in the Clinic (`clinic`)

* A study lands from PACS. A workflow runs on it. The measurement goes back as DICOM, into the tools radiologists already use.
* The model is a Docker container. The same one that ran on the research bench.
* Validated prospectively: a shadow trial first, then a clinical trial.
* No bespoke integration per algorithm. The next model reuses the plumbing.

=== Where It Has Run (`clinic-end`)

* A laptop: the whole stack in docker-compose (miniChRIS).
* On-prem at Boston Children's, wired to clinical PACS.
* The Mass Open Cloud, on OpenShift, with GPUs.
* Across institutions: FreeSurfer in the cloud feeding a multi-party computation, so two hospitals compare brain volumes without either seeing the other's data.

=== Working With It (`working`)

* Put the tool in a container.
* Give it the contract: flags, an input directory, an output directory. No prompts, no GUI.
* Describe its parameters and resource needs in the JSON descriptor.
* Register it with a CUBE. Now it can be a node in anyone's workflow.
* Try the whole stack on a laptop first: miniChRIS, in docker-compose.

The last line became the slide's takeaway.

=== What We Need to Agree (cut)

The author cut this slide on 2026-11-12. It had been in the deck since the first commit and listed four interfaces for the consortium to settle: stage contracts, app policy, the run record and a lineage mapping. It read as a meeting agenda in a talk that had become about design and principles, and its first item, an agreement on what sits between two stages, cut against the contract slides, which say an app needs nothing negotiated with the platform. One point from it is worth keeping as a spoken line on "Working With It": the contract fixes two directories and says nothing about the files inside them, so two apps in a chain still have to share a format.

=== Conclusions (`conclusions`)

* ChRIS is a workflow runtime: containers that read a directory and write a directory, chained.
* The provenance isn't bolted on. It is the directory tree the workflow leaves behind.
* It already runs clinical AI at Boston Children's, on the same contract.
* In HARBOR it is the layer inside each TD that makes local execution repeatable and auditable.
* HARBOR's work on it: one ChRIS as a peer of another, telemetry, standards. The contract stays.

The title slide's four bullets were shortened the same way. They read: ChRIS runs containerised analyses next to the data and records how every result came to exist. One rule for every app: read a directory, write a directory, exit. Chain those apps and the directory tree is the provenance record. In HARBOR it is the workflow runtime inside each Trusted Domain.
